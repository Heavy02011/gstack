1. Read **CONTEXT_REVERSE.md** to understand every domain-specific parameter.

```
git init {REPO_NAME}
```

## Phase 2 — Skill Files

Every skill lives in `{skill-name}/SKILL.md`. The structure is consistent:

### 2.1 SKILL.md Frontmatter (required fields)

```yaml
---
name: {skill-name}
preamble-tier: {1|2|3|4}
version: 1.0.0
description: {One-line description}. (gstack)
allowed-tools:
  - Bash
  - Read
  # ... subset of: Write, Edit, Grep, Glob, Agent, AskUserQuestion, WebSearch
triggers:
  - {natural-language trigger phrase}
  # 3–5 phrases that should auto-invoke this skill
# optional:
interactive: true          # if the skill asks questions interactively
benefits-from: [other-skill]   # if this skill reads output from another
gbrain:                    # if the skill reads/writes GBrain memory
---
```

**Preamble tiers:**
- Tier 1: update-check + session tracking + proactive routing rules
- Tier 2: + learnings injection + telemetry
- Tier 3: + ethos injection + proactive routing table (full)
- Tier 4: + all of above + review-army setup

**Proactive routing rules** (in tier 1+ preamble): the full table mapping user intent patterns → skill invocations. This is the same list in every skill. It is injected by the `gstack-update-check` bash block at runtime.

### 2.2 Skills to create (one directory each)

Create every skill listed in CONTEXT_REVERSE.md Section 4. For each:

1. Create `{skill-name}/SKILL.md` with correct frontmatter.
2. Write the skill body following the role's methodology. The body has these sections in order:
   - `## When to invoke this skill` — one-paragraph description
   - `## Preamble (run first)` — the bash block (auto-generated from tier; never hand-write)
   - `## Role` — the specialist persona and mindset
   - `## Inputs` — what the skill reads (design docs, diffs, URLs, etc.)
   - `## Process` — numbered steps, checklists, decision gates
   - `## Quality gates` — must-pass criteria before the skill concludes
   - `## Output` — what the skill produces (files written, PRs opened, reports)
   - `## Anti-patterns` — what NOT to do

3. Auto-generate the preamble bash block with `bun run gen:skill-docs`.

**Key skill methodology notes** (preserve these for correctness):

| Skill | Critical methodology |
|-------|---------------------|
| `/office-hours` | Two modes: PRODUCT (6 forcing questions, challenges premises, 3 alternatives) and SPEC (turns conversation into a GitHub issue). Writes design doc to disk. |
| `/plan-ceo-review` | Four scope modes: Expansion, Selective Expansion, Hold Scope, Reduction. 10-section review. Reads design doc written by `/office-hours`. |
| `/plan-eng-review` | ASCII diagrams mandatory (data flow, state machines, error paths). Test matrix. Writes test plan to disk. |
| `/plan-design-review` | Rates each dimension 0–10. Explains what a 10 looks like. One AskUserQuestion per dimension. AI Slop detection checklist. |
| `/plan-devex-review` | Three modes: DX EXPANSION, DX POLISH, DX TRIAGE. 20–45 forcing questions. TTHW benchmark against competitors. |
| `/review` | Auto-fix obvious issues with atomic commits. Flag completeness gaps. Never silently skip. Diff-scoped: only reviews changed files. |
| `/investigate` | Iron Law: no fix without root-cause. Trace data flow. Test hypotheses. Stop after 3 failed fixes — escalate. |
| `/cso` | OWASP Top 10 + STRIDE. 17 false-positive exclusions list. Confidence gate: only report 8/10+. Independent verification per finding. Exploit scenario required. |
| `/qa` | Open real browser. Click through flows. Fix bugs with atomic commits. Auto-generate regression tests for every fix. Re-verify after fix. |
| `/ship` | Lazy-load: skeleton + 8 `sections/*.md` files loaded on demand. Test run → coverage audit → plan-completion → review army → Greptile triage → adversarial pass → changelog → PR body. |
| `/autoplan` | Reads full CEO/design/eng/DX skill files from disk. Runs sequentially. 6 auto-decision principles (no questions unless truly ambiguous). |
| `/design-html` | 30KB zero-deps output. Pretext computed layout. Detects React/Svelte/Vue. Smart API routing per design type. |
| `/design-shotgun` | Taste memory persists what user likes across sessions. Generates 4–6 variants. Opens comparison board. Iterates until user approves. |

### 2.3 Skill file variants for other hosts

For hosts that need inline (non-lazy) skill content, maintain host-specific copies:
- `browse/` → full browse skill (same as root `SKILL.md`)
- Each skill has a `codex/`, `factory/`, `kiro/`, `opencode/` variant if the lazy-load pattern doesn't apply to that host.

## Phase 3 — Browse Binary

The `browse` binary is the headless browser engine. It is the hardest component; build it last if scaffolding.

### 3.1 Directory structure

```
browse/
├── src/
│   ├── cli.ts                  — CLI entry point; parses argv, dispatches commands
│   ├── server.ts               — HTTP server mode for /pair-agent

│   ├── browser-manager.ts      — daemon lifecycle; auto-start/stop; 30-min idle timeout
│   ├── cdp-bridge.ts           — CDP protocol bridge; wraps Playwright + puppeteer-core
│   ├── cdp-commands.ts         — allowlisted CDP command dispatch
│   ├── cdp-allowlist.ts        — explicit list of permitted CDP commands
│   ├── cdp-inspector.ts        — CDP inspector for extension

└── dist/
    └── browse                  — compiled binary (gitignored)
```

### 3.2 Key design constraints

- **Sub-second latency**: browser daemon starts once, persists. Commands hit running daemon (~100–200ms). Cold start ~3s.
- **State persistence**: cookies, tabs, sessions carry over between CLI calls.
- **Security**: CDP allowlist; CSP enforcement; audit log for all commands; file permissions 0o600.
- **Dialog handling**: auto-accept alert/confirm/prompt by default (no lockup).
- **Snapshot system**: four modes — interactive (`-i`, refs for click/fill), annotated (`-a`, label overlay), diff (`-D`, unified diff vs baseline), clickable (`-C`, finds `cursor:pointer` divs).

### 3.3 Build

```
bun run build            # runs scripts/build.sh
```

Output: `browse/dist/browse` (single-file executable).

## Phase 12 — Setup Script

`setup` (bash, executable) must:

1. Validate Bun is installed (print checksum-verified install instructions if not).
2. Run `bun install`.
3. Run `bun run build` (compile browse + make-pdf binaries).
4. Detect which AI hosts are installed (`scripts/host-config.ts`).
5. For each detected host, install skills to the correct path using the host adapter.
6. Create `~/.gstack/` directory structure with correct permissions (`umask 077`).
7. Install git hooks: `bin/gstack-redact-prepush` as `pre-push`.
8. Print success message with quick-start commands.

Flags:
- `--team` — switch to team mode (run `gstack-team-init`)
- `--prefix` — use `gstack-` prefixed skill names
- `--no-prefix` — use short skill names (default)
- `--host <name>` — target a specific host only

## Adapting for a Different Domain

To generate an equivalent toolkit for a different creator/company:

1. Copy `CONTEXT_REVERSE.md` to `CONTEXT_MY_DOMAIN.md`.
2. Replace every value in Sections 1–4 (creator identity, product purpose, sprint model personas).
3. Keep Sections 5–10 (design system, ethos, tech stack, security) or adjust as needed.
4. Run this plan against the new context.

**High-impact changes:**
- `CREATOR_NAME` / `CREATOR_TITLE` → changes README hero, ETHOS attribution
- `PRODUCT_DOMAIN` → changes persona descriptions and skill focus areas
- Skill personas (Section 4) → changes the specialist names and methodologies
- `AESTHETIC` / accent colors → changes DESIGN.md and all HTML outputs
- `ETHOS` principles → changes the preamble injected into every skill

**Low-impact changes (structure stays the same):**
- Skill names (they're just directory names)
- Number of skills (add/remove freely; the preamble routing table adapts)
- Technology stack (browse binary is host-agnostic; swap Playwright for Puppeteer if needed)
